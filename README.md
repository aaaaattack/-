Token exchange failed: error sending request for url (https://auth.openai.com/oauth/token)

**为什么“开全局”能解决，而“规则模式”不行**。

这背后不是玄学，而是 **Clash 分流逻辑** 与 **应用网络行为** 共同作用的结果。

### 1. 现象与表象原因（直接原因）
- **规则模式**：Clash 根据规则集（如 GeoIP、域名关键词）判断流量是否走代理。`auth.openai.com` 或 Codex 的后端 API 域名，很可能命中了 **“直连（DIRECT）”** 规则（比如被误判为国内常见域名，或匹配了 `GEOLITE` 等国际直连策略）。
- **全局模式**：Clash **无条件**将所有流量通过代理隧道转发。

**结论**：开全局后，流量强制从 `127.0.0.1:7890` 的隧道出去，成功触达 OpenAI 服务器；规则模式下，流量走了直连，因网络限制（如防火长城或运营商干扰）导致超时或连接重置，应用表现为“卡住”。

---

### 2. 深层根本原因（为什么之前没发现）
既然 `curl.exe -x` 测试能通，为什么应用之前不直接用代理呢？这涉及 **Windows 代理优先级**：

- 你的 **用户环境变量（HTTP_PROXY）是空的**，所以 Codex 没有走这个通道。
- Codex 这类桌面应用（基于 Electron 或 .NET）通常默认 **继承 Windows 系统代理（WinINET）**，而不是直接读取环境变量。
- **关键点**：在 Clash 的“规则模式”下，虽然你开启了系统代理（WinINET 指向 127.0.0.1:7890），但 **Clash 返回给应用的是“直连”指令**。对于应用来说，它尝试请求，但底层 TCP 连接超时（因为直连不通），应用又没有智能重试到代理端口，所以就卡在“等待响应”状态。
- 切换到“全局模式”后，Clash 不再返回“直连”指令，而是强制建立 CONNECT 隧道，应用瞬间就通了。

---

### 3. 为什么 `curl.exe -x` 一直能通？
`curl.exe -x` 是 **显式指定** 代理地址，它 **绕过了 Clash 的分流规则**，直接与代理端口建立隧道。这就像“走后门”一样，强制走代理，所以一直成功。这恰恰验证了 **代理服务本身是健康的**，故障点出在 **分流域名匹配** 上。

---

### 4. 解决方法

如果长期开全局导致国内网站访问变慢（因为国内流量也绕路），你可以按以下方式优化，让你既能用 Codex，又能保持规则模式：

**方案 A：添加精准的域名规则（推荐）**
在 Clash 的配置文件中（或 GUI 的“规则”页面），将 OpenAI 及其相关域名**明确设为走代理**，且放在“直连”规则之前：
```yaml
- DOMAIN-KEYWORD,openai,PROXY
- DOMAIN-KEYWORD,auth0,PROXY  # 部分认证服务
- DOMAIN-SUFFIX,chatgpt.com,PROXY
- DOMAIN-SUFFIX,oaistatic.com,PROXY
```

**方案 B：使用环境变量兜底（治本）**
即使你开着规则模式，也可以通过设置用户环境变量，强制让 Codex 绕过系统代理和分流规则，直接与代理端口通信：
```cmd
setx HTTP_PROXY "http://127.0.0.1:7890"
setx HTTPS_PROXY "http://127.0.0.1:7890"
```
设置后重启 VS Code。这样即使 Clash 规则将它匹配为“直连”，环境变量也会让应用直接去连接 `7890` 端口，相当于应用层面强制走代理（类似你的 `curl -x` 测试）。

**方案 C：Clash一直开着全局**
---

### 总结
- **现象**：规则模式不通，全局模式通。
- **本质**：Clash 规则误把 OpenAI 域名判为“直连”，导致应用直连失败；全局模式强制接管流量，避开错误规则。
- **后续**：建议按 **方案 A** 添加规则，或按 **方案 B** 设置环境变量，这样你可以继续使用高效灵活的规则模式，而无需频繁切换全局开关。
